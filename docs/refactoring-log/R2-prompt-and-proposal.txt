  Why the behaviour doesn't change

  - Error messages: all messages are copied unchanged. The two NotFoundException
    calls keep the same ("Restaurant", id) and ("Menu item", id) arguments.
  - Order of the checks: the four checks stay in one method, in the same order.
    The restaurant lookup still happens after them, so
    inputChecksRunBeforeAnyRepositoryLookup still passes.
  - Order of side effects: computeFare → save → recordFare → record is
    unchanged, which pricesThenSavesThenRecordsFareThenEmitsPlacedEvent checks.
  - Null edge cases: a null map or null user still throws an NPE at the same
    point, because the command does no work when it is built.
  - Transactions: @Transactional stays on the public method. The private helpers
    are called on this, so they run inside the same transaction. Don't annotate
    them, because Spring ignores the annotation on self-calls anyway.
  - Controller: the record constructor evaluates its arguments left to right, so
    Long.valueOf(restaurantId) still runs before toItemQuantities(). Any
    NumberFormatException or NPE still happens before the service is called.

  Design choices

  - User stays out of the command. Every other OrderService method takes (…,
    User user). The command holds what the customer asked for (from the request
    body), while user is who is asking (from the JWT). This keeps the two
    sources apart.
  - The (Customer) cast stays in placeOrder. validatePlacement could return the
    cast Customer, but then a method named "validate" would also return a value.
    Leaving it void keeps it a pure check, and the cast sits right under the
    check that makes it safe.
  - Promo code later: add a String promoCode field to PlaceOrderCommand, which
    touches only toCommand() and the test helper. Then validate it either at the
    end of validatePlacement (a format check), or as its own step between
    buildOrder and chargeCard (if it needs a repository or the order total). The
    interface signature won't change again.

  Alternatives considered

  1. Preserve Whole Object (pass PlaceOrderRequest straight to the service).
     Rejected: the application layer would depend on ui.dto, which breaks the
     layering, and restaurantId is a String there.
  2. Validation in the record's compact constructor. Rejected because it changes
     behaviour. The checks would run in the controller before the role check,
     so an operator with no coordinates would get "Delivery coordinates are
     required". That would fail roleIsCheckedBeforeCoordinatesAndCard.
  3. Replace Function with Command (a separate PlaceOrderUseCase class with
     execute(), taking 5 of the 8 dependencies). This is a reasonable next step
     if placement keeps growing after the promo code. It's too heavy for now and
     goes beyond fixing the two smells you named.
  4. A second parameter object, DeliveryDestination(address, lat, lon). This
     would be a valid Introduce Parameter Object, but it adds a type without
     removing any smell, and it would need either an Order constructor change or
     unpacking. Deferred.
  5. A builder for the command. Not needed: all 6 fields are always given at
     once, and a record covers that. It's worth reconsidering only if many
     optional fields arrive.
  6. Keeping the old 7-parameter overload and having it delegate (the migration
     form of Change Function Declaration). It isn't needed because there are
     only 2 callers, and the test brief says only the helper should change.
  7. Move Function on the card mapping (CardDetails.toPayment(amount)). It's
     tidy but optional and not part of these smells. It could be its own small
     refactoring.
